# Languages and translations

English · [Polski](i18n.pl.md)

WalkLevel speaks English (built in, the fallback) and Polish; more languages (German, French,
Spanish and others) are added as data, without code changes. This page explains the formats, how
packs reach the app, and how to add a language, a key or a translation.

## Standards

| What | Standard |
| --- | --- |
| Language codes | BCP 47 tags: `en`, `pl`, `de`, `pt-BR`. Lookup chain `pt-BR` → `pt` → built-in `en`. |
| Messages | ICU MessageFormat: `{name}`, `{count, plural, one {# step} other {# steps}}`, `{x, select, a {...} other {...}}`. Apostrophes as in ICU: `''` is `'`, `'{'` is a literal brace. |
| Plurals | CLDR categories (`zero`, `one`, `two`, `few`, `many`, `other`): `Intl.PluralRules` in the interface, ICU4X (`icu_plurals`) in Rust. No hand-written rules. A plural must list every category of its language (Polish: `one`, `few`, `many`, `other`; English: `one`, `other`). |
| Numbers | `Intl.NumberFormat` in the interface, ICU4X (`icu_decimal`) in Rust. A language may override CLDR in `locales/languages.json` (`number.grouping`, `number.groupSeparator`); Polish keeps the 0.6 look: `1 234` with U+202F. |
| Dates | DD.MM.YYYY in every language (owner's decision), only through `data()` in `src/lib/format.ts`. |
| Files | One flat JSON object per language and namespace, `locales/<tag>/<namespace>.json`. Source files carry ARB-style metadata (`"@key": {"description", "placeholders"}`) and `@@locale`; tools that read ARB (Weblate, Crowdin, Lokalise) show the description as context, plain JSON importers skip the `@` entries. |
| Direction | The document gets `lang` and `dir` from the language (`direction` in the manifest). Right-to-left layouts are not implemented yet; nothing in the format prevents them. |

Why ICU MessageFormat in JSON and not Fluent: it is the format the common translation tools
handle best (Weblate, Crowdin and Lokalise all validate ICU plurals in JSON), the Polish source
keeps its one-table workflow in `docs/texts.md`, and the same small parser runs in TypeScript
(`src/lib/message-format.ts`) and Rust (`crates/core/src/texts/message.rs`).

## Files

| Path | Who writes it | Contents |
| --- | --- | --- |
| `docs/texts.md` | people | Polish texts, keys and notes. The only place where keys are added or changed. |
| `crates/core/assets/definicje.json` | people | Names and descriptions of ranks and achievements (Polish). Shared with the account server, it does not change for translations. |
| `locales/languages.json` | people | Languages: `code`, `name` (in the language itself), `englishName`, `status` (`complete` or `in-progress`), `direction`, optional `number`. |
| `locales/pl/*.json` | `npm run texts` | Polish pack generated from the two files above, with `@key` descriptions and placeholders. Never edited by hand. |
| `locales/<tag>/*.json` | translators | Translations, same keys and namespaces as Polish. |
| `src/lib/texts-built-in.json` | `npm run texts` | Built-in pack compiled into the app (interface and Rust): English, with Polish texts for keys not translated yet, plus the language list and namespaces. |
| `crates/core/tests/fixtures/texts/cldr-samples.json` | `npm run texts` | `Intl` plural and number samples; a Rust test checks that ICU4X gives the same results. |

A namespace is the part of the key before the first dot (`glowny`, `ustawienia`, `levels`); its
file is the namespace in kebab-case (`profil_online` → `profil-online.json`). Texts of ranks and
achievements are in the `levels` namespace under `levels.rank.<level>.{name,about}` and
`levels.achievement.<id>.{name,flavor,condition}`.

## Checks

`npm run texts -- --check` (part of `npm run check`, `npm run test:ui` and CI) fails when:

- a generated file is out of date, or a message does not parse;
- a translation has a key that Polish does not have, or sits in the wrong namespace file;
- a translation uses other variables than the Polish text, a plural lacks a category of its
  language or uses one the language does not have, or a text split by ` / ` has another number of
  parts;
- a language with `"status": "complete"` lacks a key. A language `in-progress` may lack keys: the
  check prints how many, and the app falls back to the built-in pack. Keys whose note in
  `docs/texts.md` says „bez tłumaczenia” (proper names) never count as missing.

`npm run test:ui` renders every screen in Polish (all widths and themes), and at 420 px in English
and in the pseudo-language `en-XA` (accented texts about 40% longer, in ⟦ ⟧): nothing may stick
out or be cut without an ellipsis. Text without ⟦ ⟧ on an `en-XA` screenshot is typed into the
code instead of coming from `t()`.

## Translating a namespace

One person (or agent) per namespace, so work runs in parallel without conflicts.

1. List what is missing: `node tests-ui/texts.ts --missing=en:ustawienia` prints the untranslated
   keys of the namespace with their Polish text as JSON.
2. Read the context of each key in `locales/pl/<namespace>.json` (`@key.description` and the
   meaning of each placeholder) or in `docs/texts.md`.
3. Write the texts into `locales/en/<namespace>.json` (create it with `"@@locale": "en"` as the
   first entry). Keep every `{variable}` as it is, plurals in ICU form with all categories of the
   language, ` / ` separators where the Polish text has them, and the writing rules of
   `docs/texts.md` 0.1 (what happened and what to do, short, no exclamation marks). Settings paths
   („Settings > Games and controls > Control”) must use the names the screen shows in that
   language.
4. Run `npm run texts` (writes the built-in pack) and `npm run check`; fix what it reports.
5. Check the screens: `npm run test:ui` (or `npm run dev` and `/?jezyk=en`).
6. When a language has no keys missing, set its `status` to `complete` in `locales/languages.json`;
   from then on a missing key is an error.

## Adding a language

1. Add an entry to `locales/languages.json`: BCP 47 `code`, `name` in the language itself,
   `englishName`, `"status": "in-progress"`, `direction`. Add `number` only when the language
   deliberately departs from CLDR.
2. Create `locales/<code>/` and translate namespace by namespace as above.
3. `npm run texts`, `npm run check`, `npm run test:ui`.
4. Once merged into `main`, every installed version (0.6.4 and newer) can download it from
   Settings; the next release can also ship it with the installer.

## Adding or changing a key

Only in `docs/texts.md` (new keys in English kebab-case, e.g. `language.error.offline`), then
`npm run texts`. Changing the variables of an existing key breaks its translations: the check
lists them, and they must be updated in the same change. Changing only the Polish wording keeps
the translations; mention it in the review so translators can look again.

## How the app finds its language

At start (`walklevel_core::texts::packs::start_language`), first match wins:

1. A new request from the installer: `locales/installer.json` next to the exe,
   `{"language": "pl", "id": "<unique per interactive install>"}`. Applied once: its `id` is stored
   as `installer_language_id` in the shared settings, so a silent update that leaves the file as
   it was does not override a later choice in Settings.
2. `language` in the shared settings (`osoby.json`, `wspolne`; new field, empty by default, so files
   from 0.6.3 load unchanged).
3. Data from before languages (an update from 0.6.3 or older without `language`): Polish, the only
   language those versions had.
4. The Windows display language (`GetUserPreferredUILanguages`), when its pack is on this computer.
5. English.

So "English by default" holds for a new installation without a choice; `npm run dev` and a new
data folder on a Polish Windows start in Polish because its pack is in the repository.

Packs are looked up in `<data>\locales\<tag>\` (downloaded), then `<exe folder>\locales\<tag>\`
(installed), then the built-in pack. When running from the repository (`tauri dev`, tests) the
exe folder is the repository root, so `locales/pl` is used directly.

### Download

Settings > Appearance and window > Language lists the built-in languages, the installed and
downloaded ones, and the languages from `locales/languages.json` on `main` in the repository
(fetched when the card opens; without internet the list stays local). Choosing a language that is
not on this computer downloads every namespace this version knows from
`https://raw.githubusercontent.com/<repo>/main/locales/<tag>/<namespace>.json` (HTTPS, this host
only, at most 512 KB per file) into a temporary folder, then moves it to `<data>\locales\<tag>\`
with its manifest entry (`_language.json`). A namespace missing in the repository is skipped (its
keys fall back to the built-in pack). Every text is checked against the built-in pack: unknown
keys and texts with other variables are dropped, so a newer or older pack never shows a broken
message. Errors (no internet, HTTP status, damaged file) go to the error card with a retry button.
When the chosen language is still missing at start, the app shows the built-in pack and downloads
it in the background.

### Switching without a restart

The core switches its texts (`texts::set_language`), rebuilds every state slice (statuses, hints,
names of modes and achievements) and sends the `language` slice. Each window reloads the packs
(`language_pack`); the main window also reloads the static data and rebuilds its views
(`{#key}` in `App.svelte`); open Settings categories stay open. Texts the core already stored as
text (the last toast, a finished download message) stay in the language they were made in.

## Installer (next step)

Designed now, built in the installer task:

- First page: the installer's own language (Inno Setup `[Languages]`, English default, Polish).
- Then a component list of app languages: English (checked, fixed: it is built in), Polish and
  later others (unchecked by default, checked when the installer runs in that language). Each
  component installs `locales\<tag>\*.json` into `{app}\locales\<tag>\`. Inno keeps the selection
  for updates (`UsePreviousComponents`), so `/VERYSILENT` from "Update" keeps it.
- Start language: the installer's language when its pack is selected, otherwise English. Written
  to `{app}\locales\installer.json` as `{"language": "<tag>", "id": "<timestamp>"}` only in an
  interactive install (`not WizardSilent`); a silent update leaves the file alone.
- An update from 0.6.3 (no previous selection): preselect Polish, because those users used the app
  in Polish; the app also falls back to Polish for their data (rule 3 above).
- `packaging/build.ps1` copies `locales\<tag>\` (not `en`, which is built in) next to the exe.

## Account server

Messages from `/api/bieznia/*` (`message`) are shown as they come, so today they are Polish in
every language. The app now sends `Accept-Language` (`en, pl;q=0.5`) with every request, and
when an error reply carries a stable `code` (`[a-z0-9_-]`, e.g. `invite_invalid`) and the key
`konto.serwer.<code>` exists, it shows its own text in the current language instead of
`message`. Needed from the server: a `code` next to `message` in error replies (and optionally
messages in the requested language). No server change is required for this version.
